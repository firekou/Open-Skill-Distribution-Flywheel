G3 cancel semantics — 2026-09-19T18:56:31Z

One word, 'cancel', was covering four actions that stop different things.
Separated, each with what it CANNOT do stated:

  L1 stop dispatch      STOP file, read before every action.
                        Stops the NEXT runner. Does not touch one already running.
  L2 cancel one task    CANCEL-<task> file, read at that task's next checkpoint.
                        Ends that task only. Does not touch a running runner and
                        does not stop other tasks.
  L3 terminate runner   kills the runner AND every process it started.
                        Does NOT undo a commit the runner already pushed.
                        That needs a revert: a separate authorised action.
  L4 revoke credential  NOT POSSIBLE FROM THIS PROGRAM. Only the issuer can
                        revoke a key - the Anthropic console for the model
                        credential, GitHub for the token. If a runner leaked
                        or misused one, L1-L3 do not take it back.

== The L3 defect, measured ==
subprocess.run(timeout=...) kills only the direct child. A CLI agent that
starts its own worker leaves that worker running, still holding the
credentials that were in its environment.

-- plain kill, which is what the code did --
mode=plain  direct child killed=True  grandchild still alive=True
-- process-group kill, which is what it does now --
mode=group  direct child killed=True  grandchild still alive=False

Note on measuring this: os.kill(pid, 0) is NOT a liveness check. A killed
process whose parent is gone stays a zombie until reaped, and in this
container pid 1 never reaps it, so signal 0 keeps succeeding for a process
that is thoroughly dead. The first version of this test AND its negative
control both asked that wrong question, which would have let the control
pass without reproducing anything. The tests read /proc/<pid>/stat instead.
