# ATK 工具寶庫：外部 Agent 發現、採用與解題驗收

## 負責人最新目標（2026-09-18）

原始目標維持：找到有用工具／skill → 整理改善與驗證 → 透明可選地接入 ATK Router／API／MCP → 技術分享與分發 → 外部 agent 實際找到、採用、完成任務。

「寶庫」的價值來自外部 agent 遇到問題時能找到合適資產，理解適用範圍，順利使用並解決問題。工具數、文件數、star、曝光及本機測試數不能代替這個結果。持續向外搜尋與更新工具，也要持續讓別人的 agent 能向內搜尋並取用成果。

負責人的「必然發現、容易採用」是必要的產品目標；任何 agent 都必然找到不是目前可證明的事實。以指定任務、搜尋入口和實際執行證據求證，記錄找不到、裝不起來與解不了問題的失敗，不以口號宣告達成。

## 當前狀態

PR #4 的 829c7e9 小型接入範例已通過約定審查；這只結束該修復輪。實際候選工具整合、外部發現、分發成效及外部採用尚未證明，整體專案不能結案。

停止點是單次交付的交接點。Reviewer 完成一輪後，應指出下一個尚未證明的目標及最小驗證任務，持續推進；已解問題不無限加測。Benchmark 與治理 PoC 不因此恢復。

## 每份可分發資產要回答的問題

| 階段 | 最小交付 | 求證方式 |
|---|---|---|
| 找得到 | 面向問題的名稱、描述、標籤、公開稳定入口；人可讀清單及機器可讀索引 | 給 agent 真實問題，不提供答案網址或資產名稱，記錄它透過指定外部搜尋入口是否找到 |
| 選得對 | 適用／不適用情境、輸入輸出、依賴、授權、限制與證據版本 | agent 說明選擇理由；不適用案例應拒用或選其他方案 |
| 用得起來 | 釘選版本、最短安裝／設定／執行指令、小型輸入、預期結果、憑證需求 | 乾淨環境按公開說明走完，不靠作者私下提示 |
| 解得了題 | 與實際用途相符的工作成果 | 檢查任務的具體成功條件，不只 HTTP 200 或 exit 0 |
| 值得再用 | 更新日期、維護狀態、相容性、回饋與回報錯誤入口 | 記錄獨立使用與再次使用；無外部使用紀錄就標未知 |

採用 ATK 保持透明、可替換、可移除。發現與閱讀資產不要求先提供 API key。付費步驟、外送資料與必要權限在執行前說清楚。第三方工具保留來源與授權；未獲再分發權時提供連結／設定，不複製其程式。

## Claude 下一個具體交付：一個真實工具的完整發現與採用路徑

1. Fetch 最新 main 與已核准 PR #4；依 AGENTS.md 與既有 skills 工作。不要重開 PR #4 的已解修復，也不要自行合併它。
2. 從現有 registry 挑一個真實工具，閱讀上游實際程式／官方文件，確認版本、授權與原生 base URL／provider 設定。先求證，不沿用「可能要 fork」「所有工具都需要 adapter」的假設。現有候選不適合時再向外搜尋，記錄排除理由。
3. 完成該工具的一個具體任務與可選 ATK 接入。原生設定足夠就使用設定，無需增加共用 SDK。若依賴 PR #4 未合併成果，明列釘選版本與 PR 依賴；不要把分支中的檔案描述成 main 已安裝。
4. 交付公開導覽頁與一份小型機器可讀索引，優先擴充既有 registry，不另建平台。每筆至少包含：穩定 ID、解決的問題、入口、版本、授權、安裝／範例、輸入輸出、ATK 設定、替代 provider、費用／權限、驗證日期與證據、維護狀態。檢查連結可取用。JSON 或 Markdown 是交付形式，不代表搜尋服務一定收錄；不把 llms.txt 或 MCP 當成自動被發現的保證。
5. 小規模做兩種明確分開的驗證：
   - **可尋址／可採用試驗**：給入口網址但不給逐步操作提示，乾淨 agent 環境能否找對工具並完成任務。這不叫自然搜尋發現。
   - **外部發現試驗**：以三個真實問題表述開始，不給 repository 名稱、品牌、資產網址或挑選答案。記錄 agent／搜尋工具、時間、查詢、結果、實際選到的資產及後續操作。找不到就如實記失敗與最小改善。三個案例是初步診斷，不能估算普遍發現率。
6. 人工安排的隔離 agent 試用只證明受控條件下可用，不能當作外部使用者自發採用。外部採用需第三方實際使用的可核對紀錄；在既有交接檔記錄即可，不為追蹤先建遙測平台，也不收集秘密 prompt／key。
7. 完成一份分享稿及具體分發清單：每個入口的讀者／agent 如何看到資產、連到哪裡、如何驗證有被收錄與使用。先沿用自有 GitHub 和既有渠道；外部目錄依其規範準備提交資料。沒有實際投放就標待發布，不能把計畫寫成已分發。
8. 必要真實執行需在已有憑證授權與預算範圍內進行；缺 access 時完成其餘工作，精確標示阻擋。不複用已暴露憑證、不提交秘密、不自行擴大付費工作負載。對外訊息、社群發布、第三方提交依既有授權界線處理，資料先備齊。
9. 在新工作分支提交、送 Draft PR，不合併；回覆於 reviews/ATK_AGENT_DISCOVERY_EXECUTOR_RESPONSE.md。內容包含本輪五行目標對齊、精確 SHA、證據、失敗案例、剩餘缺口及下一個最小實驗。完成交付後等待 reviewer，reviewer 判定後接續尚未達成的目標。

## Reviewer 判定與停止規則

沿用 executive-review-gate，不新增批准制度。每輪分開說明：
- 程式／資產是否符合本次驗收。
- 公開入口是否真能被取用。
- 是否在受控條件下被找到、採用、解題。
- 是否有外部自然發現、第三方使用、重複使用證據。

證據不足就保留未知，不以 AI 彼此同意升格為 VERIFIED。發布尚未授權／索引尚未收錄／第三方尚未試用時，持續完成可做準備並列下一個具體檢查，不能宣稱總目標完成，也不在背景無限循環。

本文件是工作指令與驗收要求，不是已建成搜尋系統、已執行試驗或已啟動背景 agent 的證據。

## 商業假設補充：價值回收與 50～100 Agent 供應能力

### 目標與假設分開

負責人新增的必要目標：外部 agent 取得有用服務後，ATK 能回收收入、可辨識品牌傳播或有價值的使用回饋；以模組化 agent 組織擴大供應，目標具備 50～100 個角色／工作單元的營運治理能力。

待求證假設：agent 搜尋需求會成長、願意採用 ATK 供應、願意付費或接受明示的品牌交換、擴充後單位服務仍有正向收益。以上不是因為具備協議或增加 agent 數就已成立。

付費權限來自 agent 背後的使用者／組織。角色數、同時執行數、完成任務數分開記錄；不預設 100 個角色必須常駐 100 個程序。

### 兩條價值交換路徑

| 路徑 | 交付內容假設 | ATK 回收 | 必要驗證 |
|---|---|---|---|
| 免費且附品牌／贊助資訊 | 可用的基本工具、解答、來源、範例，明示 ATK 提供／贊助與服務連結 | 可確認來源引用、品牌呈現、導流、使用回饋 | 外部 client 是否接受、是否保留標示、是否使用及返回；僅傳送廣告欄位不算傳播成功 |
| 付費附加服務 | 按任務整理、更新追蹤、更深入驗證、整合協助等，依需求選一项試驗 | 實際入帳的服務收入 | 價格與交付範圍、付款授權、成功交付、失敗處置、重複使用及單位成本 |

免費服務的品牌內容應明確標示，與答案、證據、推薦理由分開。不得把業配包成獨立評測結論，也不使用隱藏指令要求下游 agent 無條件推薦 ATK。可在服務條件中明示署名要求並確認 client 接受，但無法靠回應內容保證所有下游系統都會展示。第三方工具原授權不因 ATK 包裝而被額外限制。

請求紀錄只證明伺服器收到请求；回傳成功只證明交付；client acknowledgement 是 client 自報接收；引用、完成任務、再次使用與付款應分開求證。回饋是選擇加入的用途明確資料，不能把「服務有價值」當成索取第三方機密的授權。

### Handshake 的最小商業內容

不要先發明新協議。先定義交易雙方必須理解的內容，再映射客戶端實際支援的 HTTP／MCP 等介面：

1. 能力與版本：能解什麼問題、輸入輸出、限制、來源與更新時間。
2. 方案與條件：免費／付費差異、品牌標示、價格單位、資料用途。
3. 授權與上限：誰付款、允許做什麼、預算與期限；重試不能造成重複收費。
4. 交付與回執：請求 ID、結果、來源、付款狀態；失敗如何恢復或退款。
5. 回饋：任務是否完成、是否引用或再次使用，避免把回饋自報等同獨立證明。

已核對官方資料（2026-09-18）：[x402 官方介紹](https://docs.x402.org/introduction) 提供 HTTP 402 的程式化付費存取流程；[Google AP2 官方說明](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol) 描述 agent 購買授權與可核對的委託。兩者是不同問題的候選元件，不表示 ATK 已整合、每個 client 都支援或市場已願意付款。既有帳戶／額度扣款若足夠，不強制導入錢包。

### 治理方向更新

負責人最新指示允許為 50～100 agent 的服務供應能力研究、選用與驗證更好的治理工具。先前暫停「無具體用途便導入治理平台」不代表永久禁止治理，也不自動恢復 Omnigent／AGT／OMA 原 PoC。

以實際瓶頸選工具：任务佇列與擁有者、版本與輸入輸出契約、權限隔離、預算限制、重試／冪等、獨立評審、狀態可見、故障恢復、人工接管。優先現成能力，不同工具必須對應不同必要功能，避免重複疊加。

建議驗證順序而非現成能力宣稱：
- 先以小組跑通一項外部任務，驗證可採用與價值交換。
- 有需求或可重播工作負載後，分階段驗 10、25、50，最後至 100 工作單元；先用合成故障／離線工作負載控制成本，與真實需求分開報告。
- 每階段記成功交付率、每件成本、返工、等待時間、權限違規、人工介入與重複付款／執行。擴充前依服務承諾訂門檻，未達則修瓶頸，不繼續加 agent。
- 角色多或產量大不代表全球市場被滿足；要有跨來源外部需求、付費或採用回報。

### 下一工作包的商業驗證補充

沿用上方一個真實工具的發現與採用任務，不另起平台。同一份 executor response 加入：
- 一個具體外部需求與現有替代方案；現階段有何理由選 ATK。
- 同一服務的免費品牌版與付費增值版樣本，具體說明多付錢買到什麼。先做可審閱樣本，不自行上線收款。
- 用選定 client 驗證來源／贊助標示與回饋是否能保留，未支援就記失敗。
- 分開統計服務收入、免費流量帶來的 ATK 使用毛利；避免把同一筆收入重複計算。每件貢獻 = 實收服務收入 − 模型／搜尋／運算／支付／交付與返工的變動成本；公司獲利還需扣固定成本。曝光與讀取不按收入入帳。
- 提出一個有具體瓶頸證據的治理工具選擇或「現有能力足夠」結論，先查既有收藏，再查外部官方來源。
- 負責人最新目標不等於新增花費、對外發布、收款帳戶或部署授權；先把上述方案與驗證做成可審閱成果，再處理真正的資源決定。

本節將規模化治理與商業回收納入主線，但仍從最小可用服務與需求驗證開始。不要用研究支付協議取代有用服務，也不要用增加 Agent 數取代採用與收入證據。
