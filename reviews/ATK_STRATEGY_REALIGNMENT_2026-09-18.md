# ATK 技術分發與 Router 接入：目標校正
日期：2026-09-18
依據：負責人本輪明確指示，回到搜尋有用 skill／AI 工具、技術分享與結構建設、ATK router 植入。此為目標與排程修正，不是 benchmark 通過判定。

## 1. 審查結論與責任

方向已出現實質偏移。原始 ATK_OPEN_SKILL_STRATEGY.md 的主線是 Discover → Improve → Integrate → Publish → Use，北極星是實際透過 ATK 使用的專案。後來 README 與執行文件把研究、Lab、Verify、Benchmark 放到整合之前，並把量測與信任擴張為中心議題。

Reviewer 的責任有三點：
1. 以發現／修掉更多 benchmark 缺陷當作進度，未先判斷 benchmark 是否仍值得做。
2. 把工具可靠性的技術需求，推演成 ATK 應轉向量測產品的商業結論。缺陷證據不能證明客戶願意購買量測工具。
3. 在用戶要求治理防止偏航時，又提出建置新調度與治理系統，進一步增加支線。

過去對 benchmark 的局部測試與缺陷發現仍有效。用戶曾同意探索或修復，不代表每個後續擴張都自動成為公司方向。最新目標澄清優先。

## 2. 唯一主目標

透過發現、整理、改善和分享有用的 AI skill、工具、工作流與範例，建立 ATK 自有技術分發資產，讓開發者在解決實際問題時，能透明、可選擇地接入 ATK Router／API／MCP，並促成可觀察的實際使用。

植入代表有用的接入位置、範例、設定、文件與維護，不是隱藏導流或強迫綁定。能用薄 adapter、原生 provider 設定或可運行範例解決，就不另造 Router、SDK 或治理框架。

## 3. 明確暫停與保留

| 工作 | 新狀態 | 理由 |
|---|---|---|
| 通用 Token Efficiency Lab／方法論凍結／正式 benchmark | PAUSED_BY_STRATEGY | 不是當前分發與接入交付的前置條件 |
| R4-01 至 R4-06 的全面修復排程 | 暫停自動續跑 | 缺陷保留為 OPEN；暫停不等於 CLOSED 或批准使用 |
| Measurement & Trust 成為產品中心 | 未採用，列研究備忘 | D007 原本就是缺需求證據的 STRATEGIC BET |
| Omnigent／AGT／OMA 安裝與協作 PoC | 暫停 | 尚未證明是交付首批資產的必要瓶頸 |
| 已有 registry、來源資料與授權查核 | 保留並重用 | 能直接支援選題與整合 |
| reviews/、既有審查 skill、版本與基本測試 | 保留但縮小適用範圍 | 服務交付與防偏航，不自成平台 |
| 工具分享、可運行範例、ATK 接入與維護 | 主線 | 直接服務原始目的 |

本次不刪分支、不關 PR、不把未通過的 benchmark 合併或發布。若日後某一特定對外主張需要量測，只建立支持該主張的最小實驗，不先恢復整套研究平台。

## 4. 三條產出路徑，不能混成一個長關卡

### A. 技術精選與分享
回答：工具幫誰解決什麼問題，怎麼用，限制是什麼，原始來源在哪。
不需要每項都有 ATK adapter；少數純價值分享是合理的。不能把廠商自述寫成自家已驗證，也不能所有選題都無限延後到 benchmark 完成。

### B. 可运行 ATK 接入資產
回答：哪個真實工作流有模型呼叫接點，接上 ATK 需要改什麼，使用者如何切換供應商。
優先選原生設定、薄 adapter、demo；只有確有維護價值且權利允許才 fork。
驗收限於承諾的功能：安裝、所需 API 功能、錯誤處理、provider 切換、key 不外洩、文件可跟做。沒有宣稱省錢就不要求證明節省百分比；若宣稱省錢或品質不降，則另需相應證據。
ATK endpoint、model ID 與能力依實際服務確認，舊規格中的示意值不當成已驗證服務。

### C. 分享到採用
每個接入資產配 Quick Start、示範與少量技術內容，指向可用專案。
觀察外部是否能跑通、在哪一步卡住、是否啟用 ATK。只記取得到且允許記錄的資料；沒有後端證據就說未知，不以 stars、clone 或閱讀量冒充 API 使用。

主循環：選用戶問題 → 找現成工具 → 做有用的分享或最小接入 → 必要驗證 → 分發 → 使用回饋 → 改善。

## 5. 下一個工作包

先從現有 registry 與 Top Integrate 名單選三個候選，不重做全網搜尋。每個只需五個欄位：
- 具體使用者與工作問題。
- 現成專案與採用理由。
- 模型呼叫點／ATK 可加入位置，或純價值分享的明確理由。
- 最小可交付資產與必要驗證。
- 维护負擔、放棄條件與通往採用的路徑。

選一個接點清楚、能做小改動的候選先交付：一個 runnable example 或薄接入、一份 Quick Start、一份含限制的驗證紀錄、兩篇技術分享草稿。這是新提議的首個小批次，不是已完成成果，也不是保證期限或數量業績。

若缺 credential，先完成可離線檢查的配置與文件，明列 live 驗證缺口，不能自稱可用。既有授權範圍內繼續；不自行購買資源、發布到社群或發送上游訊息。

Claude 將候選與交付進度寫入 reviews/ATK_DISTRIBUTION_EXECUTOR_RESPONSE.md。Reviewer 首先驗方向，其次才驗技術。不要把整個 benchmark 修完列為此工作包依賴。

## 6. 治理先檢查方向，再檢查實作

每次派工前只回答：
1. 這項工作服務原始目標的哪一步？
2. 使用者拿到什麼可用資產？
3. ATK 接入或採用路徑在哪？純價值分享則說明其分發作用。
4. 到哪個可驗收成果就停止？
5. 這是在驗證既定交付，還是在偷偷改產品方向？

若無法回答，技術主管應縮小或取消工作，而不是建立新的框架處理它。
Reviewer 同樣接受這五題，不能因自己找到更多缺陷就自動增加研究範圍。

一般修復由 agent 自行處理，不每項交回負責人。更換客群、產品中心、商業模式、重大預算或對外承諾，才屬於負責人的方向決策。新的「策略假設」不等於已授權產品化。

近期看：可用技術資產是否交付、ATK 接入是否跑通、外部使用者是否能跟做、使用障礙是否減少。
商業北極星保留原本 MAAPP：月內實際透過 ATK 執行工作的專案數；未有可信資料前不捏造數字。
不以測試數、review 輪數、文件量、agent 數或架構複雜度宣稱接近商業目標。

目前核對到的是策略、registry、benchmark 修復與審查文件。這些不能證明已形成分發 → ATK 活化閉環。本次未全量盤點其他 repository 或後端，因此不聲稱整個 ATK 沒有任何整合或用戶。
