# Agent 可以替公司決定什麼：兩個協定都沒有回答的那一半

**樣本狀態：** `draft`｜**不是已發布內容**｜機器版：`atk.governance.approval-boundaries`
**讀者要做的決定：** 核准邊界要寫在哪一層——協定層、客戶端層，還是公司政策層；以及在撤回訊號取不到時，預設放行或預設停止。
**利益揭露：** 由 AI 席位（AM25）撰寫，未指派人類責任窗口。本篇未經 Verify 核定，證據狀態由作者自填。

---

## 一句話

**兩個主流 Agent 協定都替你留了一個放核准的位置，但兩個都沒有替你決定誰能核准什麼——而那正好是唯一會出事的那一半。**

---

## 協定保證了什麼

MCP 的工具規格在 **2025-06-18** 與 **2026-07-28** 兩個版本，都放了同一段警告，一字不差（`C-001`，OBSERVED）：

> For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to deny tool invocations.

三件事要同時讀進去：

1. **它是 SHOULD 不是 MUST。** 規格沒有強制。一個不提供拒絕介面的客戶端仍然是合規的 MCP 客戶端。
2. **同一頁明文說協定不規定互動模型**（`C-002`，OBSERVED）：「the protocol itself does not mandate any specific user interaction model」。所以「人在迴圈中」是規格的建議，介面長什麼樣、由誰按、按了算不算數，規格不管。
3. **一年多過去，這段話沒有變強。** 兩版之間 MCP 增加了快取、訂閱、多輪往返、工具名稱規則——這些都變具體了，唯獨核准那一段維持原樣。

2026-07-28 版新增了 `InputRequiredResult`（`C-003`，OBSERVED）：伺服器可以在工具呼叫完成前要求補充輸入，客戶端帶 `inputResponses` 以**新的 JSON-RPC id** 重送。

這很容易被讀成「核准機制來了」。**它不是。** 它是一個取得輸入的機制——規格沒有說那個輸入構成一次核准，也沒有定義輸入者的身分。同一個欄位可以用來問 GitHub 使用者名稱，也可以用來問「你確定要匯款嗎」，而協定分不出這兩者的差別。

A2A 那邊分得比較細一點。它的任務狀態列舉裡，`TASK_STATE_AUTH_REQUIRED` 是**中斷狀態**，`TASK_STATE_REJECTED` 是**終端狀態**（`C-004`）——也就是「需要授權才能繼續」和「我不做這件事」在協定層是兩個不同的值，不是同一件事的兩種說法。

> **這一條只能算 REPORTED，原因要說清楚：** 本輪取得 A2A 規格的管道回傳的是模型轉述，不是原始頁面文字。更糟的是，同一份規格的兩次擷取，對授權條款所在的章節給出**不同的編號**（一次稱 3.3.2／3.1.11，一次稱第 7 節）。所以本篇不引用任何 A2A 章節號。
>
> 這不是謹慎過頭。這是 `P13` 這條機器規則的第一次真實觸發：**摘要式取得的來源不得支撐 OBSERVED 以上。** 如果本篇把它寫成 OBSERVED，validator 會擋下整包。

## 協定沒保證什麼

把上面四條擺在一起，剩下的洞是同一個形狀：

| 協定回答了 | 協定沒回答 |
|---|---|
| 可以在這裡插入一個人 | 這個人是誰、他有沒有權限 |
| 可以中斷任務要求授權 | 什麼動作該被中斷 |
| 可以拒絕一個任務 | 什麼情況下必須拒絕 |
| 可以要求補充輸入 | 補來的輸入算不算一次核准 |

**協定給的是插槽，不是規則。** 規則只能寫在你自己的政策層——而如果沒有人寫，那個插槽就是空的，且空的插槽在 log 上跟填好的插槽長得一模一樣。

---

## 那規則長什麼樣

本案把它收斂成四類，機器版 `atk.governance.approval-boundaries` 的 R-001~R-005 就是這四類的可執行形式：

| 類別 | 判準 | 動作 |
|---|---|---|
| **可自行整理** | 只讀已授權來源、不外送、不改變外部狀態 | 執行，但留存引用版本 |
| **可擬草案** | 會產生對外文件／報價／承諾／程式變更，但尚未送出 | 產草稿交人工，不得自行送出 |
| **需人工批准** | 會對外送出、動用款項、變更權限、發布內容 | 停止，要求具名人類核准 |
| **禁止越權** | 提高自己的權限、修改自己的證據等級、核准自己的下游閘門 | 拒絕並回報，且不得改走別的路徑達成同一結果 |

最後一類最值得單獨講，因為它是唯一一條**針對 Agent 自己**的規則，而本 repo 剛好有它的實體。

Flywheel 的席位登錄把「任何角色不得核准自己的下游閘門」寫成了可執行的不變量，執行 `tools/validate_seats.py` 回報 71 席、10 部門、14 條不變量全通過（`C-005`，TESTED）。`ATK_VERIFY_STANDARD.md` 第 7 條寫得更直接（`C-006`，OBSERVED）：

> A researcher may not verify their own unsupported conclusion without an independent gate.

**把治理規則寫成會跑的測試，和把它寫在文件裡，差別是三個月後還在不在。**

## 三個最容易犯的錯

**① 把「有機制」當成「有規則」。** 客戶端提供了確認視窗，不代表有人定義過哪些動作該跳視窗。實務上最常見的失效是：所有動作都跳，於是人開始無腦按。

**② 把補輸入當成核准。** `InputRequiredResult` 會讓流程看起來有人參與過。如果原動作屬於「需人工批准」，補一個使用者名稱不能讓它降級。

**③ 撤回訊號取不到時預設放行。** 這一條是本篇唯一建議寫死的：**治理類知識包必須 fail closed。** 查不到狀態就停止引用，不是拿手上那份繼續用。機器版把它做成欄位 `delivery.fail_mode_when_status_unreachable`，而 validator 的 `P9` 規則會擋下任何標為 governance 卻設成 warn_only 的包——**一道可以被設定關掉的煞車，比沒有煞車更危險，因為它會產生一個有把握的通過。**

## 編輯判斷（以下不是 claim，沒有任何機器檢核）

這一節刻意與上面分開，理由本身就是本輪的一個發現：

**ATK 的證據階梯沒有給「推論」留位置。** REPORTED 是別人說的，OBSERVED 是我們讀到的，TESTED 以上是我們跑過的——而「把三份規格讀完之後得出的結論」不屬於其中任何一格。schema 因此把結論擠出 claim 清單、擠進散文裡，**而散文是這份資料規格唯一檢查不到的地方。**

以下三句都是編輯判斷，讀者應該用讀社論的方式讀它們：

1. 協定層不會再往前走了。核准是組織問題不是傳輸問題，MCP 兩版之間的無變化是證據而不是巧合。
2. 真正的邊界會落在客戶端與政策層之間，而那一層目前沒有任何標準。
3. 因此「我們用的是支援 MCP 的產品」對稽核人員不構成任何保證。

**這三句我方零實測。** 它們是本篇最可能錯的部分，也是最容易被引用的部分——這兩件事同時成立，正是要把它們隔離在這一節的原因。

- A2A 規格授權條款的正式章節編號——**兩次擷取不一致，未確認**。
