# ATK 目標對齊與防偏航

## 目標與適用範圍

本 skill 同時約束規劃者、執行者與 reviewer，尤其是提出下一步的 AI。當工作只涉及已批准範圍的小修正，沿用現有目標摘要即可，不新增一輪審批或文件。

目前目標：搜尋、整理、改善與分享有用 AI skill／工具／工作流，交付可用技術資產，讓使用者透明、可選地接入 ATK Router／API／MCP，促成實際採用。

最新使用者明確指示優先於本 skill 與歷史計畫。不要把 2026-09-18 的暫停決定變成永遠禁止 benchmark 或治理工具的規則；若使用者日後明確改變方向，更新適用目標並保留決策歷史。

專案脈絡依需要讀取：
- 根目錄 `ATK_OPEN_SKILL_STRATEGY.md`：原始分發與接入目的。
- 根目錄 `reviews/ATK_STRATEGY_REALIGNMENT_2026-09-18.md`：已發生偏航與校正。
- 根目錄 `reviews/STATUS.md` 與本輪工作檔：當前狀態。
這些是 repository 相對位置。缺檔時使用可見用戶指示，註明缺口，不自行補造批准紀錄。

## 在四個時點啟用

規劃／派工前；新增依賴、框架或研究題目前；開始下一輪修復／review 前；宣告完成與建議下一步前。

先用五行寫在既有任務或 review 中，不另建治理專案：
- 目標來源：最新明確指示或已批准文件。
- 本輪交付：哪個使用者拿到什麼可用成果。
- 主線連結：對技術分享、ATK 接入或實際採用的具體作用。
- 必要驗證與停止點：驗哪項承諾，達到什麼就交付。
- 範圍差異：是否新增了產品方向、工作或依賴。

不能只寫「提升信任」「建立基礎」「長期重要」。說出這項工作被刪掉，眼前哪個交付會失敗。純技術分享可有獨立分發價值，不必每篇硬塞 ATK adapter；但持續沒有接入路徑的組合必須重新取捨。

## 決策順序

1. **先驗目標。** 沒有主線連結就縮小、列待辦或停止支線。不要先完整技術 review 再問值不值得做。
2. **選最小足夠交付。** 原生 provider 設定能解決，就不另造 SDK；薄 adapter 能解決，就不另建平台。若較大架構是必要條件，指出具體限制與替代方案成本。
3. **保留必要品質。** 不得以防偏航跳過本次承諾涉及的安裝、API 功能、provider 切換、資料安全或授權檢查。有對外節省／品質主張，就需要相應證據；沒有該主張，不預設通用 benchmark 是發布前提。
4. **限制 review 範圍。** 新發現只有影響當前交付、安全或其對外主張時才阻擋；其餘明列待辦。達到原定驗收就結束，不以更多測試或零缺陷為無限目標。
5. **必要時處理方向變更。** 可逆且在範圍內的技術選擇自行完成。更換客群、產品中心、商業模式、重大預算或對外承諾，先提出具體差異與可選方案，不能藏在「技術必要」裡。既有授權足夠時不重問。

## 本次失誤必須轉成的行為

| 已發生的錯誤 | 今後應採取的行為 |
|---|---|
| 把 benchmark 發現更多缺陷視為商業進展 | 分開報告技術修復成果與分發／接入成果；前者不自動證明後者 |
| 因省 Token 數字不可信，推論 ATK 應做量測產品 | 只縮小或撤回無證據的主張；新產品需要獨立需求與使用者方向決定 |
| 把 STRATEGIC BET、AI 共識或高 Star 當成已批准方向 | 明列假設與授權來源，不能從「值得研究」升格成「應建置」 |
| 讓 Lab、Freeze 成為所有內容與整合的前提 | 對每個交付列其必要驗證，不把特定實驗的門檻套到整個業務 |
| 用安裝治理框架回應失控感 | 先縮小任務、釐清權責與停止點；有具體瓶頸才選工具 |
| 已投入很多輪，因此繼續修下去 | 只按未來交付價值與剩餘成本取捨，不用沉沒成本支持續作 |
| 每輪 review 自動派生下一輪 | 先重核必要性；重複阻塞且沒有新證據時，縮小交付或記錄停止 |
| 文件寫完成，卻沒有可用成果 | 分辨規格、實作、實測、外部採用，不用文件數／測試數冒充使用 |
| 停止支線後，把未解缺陷當已解 | 記 PAUSED 或 DEFERRED，保留 OPEN finding，未通過程式不得冒充可用 |
| 只修文件其中一處，舊入口仍叫 agent 繼續 | 更新相關執行與 review 入口，保留歷史但清楚標明被取代內容 |
| 要使用者搬運兩個 AI 的技術對話 | 在 reviews/ 直接交接；只向負責人報重要進度、風險與真實決策 |

## 發現偏航時

指出「原目標 → 現任務 → 多出的假設或依賴」，停止擴張該支線，保留成果與缺陷。提出能回到主線的最小工作包。依已授權範圍更新任務與入口；本 skill 不授權 push、merge、安裝、花費或部署。

不要把暫停 benchmark 當成整個專案停止。也不要為補救偏航再建立新平台、長篇方法論或額外 agent 組織。已有校正足夠時，直接照其交付。

## 完工與主管彙報

沿用既有 executive-review-gate 的證據與審查結論，不建立另一套 PASS 名稱。開頭額外清楚說明「本輪仍符合原目標／已偏離，理由是什麼」。

對負責人只報：
- 本輪交付了什麼，如何推進原始目的。
- 真正驗證到哪裡，還有哪些會影響採用的缺口。
- 下一個最小成果與停止點。
- 是否需要商業方向決定；沒有就寫無。

長期觀察實際 ATK 活躍專案，近期觀察可用資產、接入跑通與外部使用回饋。沒有資料就記未知；本 skill 不要求先建完整數據平台。

## 邊界情境自查

- 使用者要一篇工具介紹：查來源、限制與用途即可；不得加上先建 100-run benchmark 的要求。
- 要發布省 30% 的主張：要求對應證據或刪除該主張；不得用「回歸分發」免驗。
- adapter 明確暴露 key：修復並驗證後才能交付；不得移到非阻擋待辦。
- 舊 benchmark 有未解錯誤但已暫停：保留未解狀態，不阻擋無依賴的工具分享。
- 使用者明確授權研究量測產品：按新範圍做研究，不用舊目標拒絕；研究仍不等於自動授權產品化。
- 要求一般修復且目標沒有變：完成修復，不要求使用者再次批准整個策略。

這是供 agent 讀取的工作規則，不是程式化強制控制，也不保證永遠不偏航。每輪可觀察的目標對照、取捨與交付才是是否遵守的證據。
